# Правила работы над проектом ИС «Каршеринг»

Единый свод правил для всех участников проекта. Документ связан с issue
[#1](https://github.com/sumply/Carsharing-MMU/issues/1): issue не закрывается и дополняется
по мере разработки. Изменения сначала вносятся в issue, затем в этот файл — расхождений
между ними быть не должно.

## Стек проекта

| Компонент | Выбор | Примечание |
|---|---|---|
| Платформа | .NET 10 | `TargetFramework` = `net10.0` |
| Веб-фреймворк | ASP.NET Core Web API | контроллеры, Swagger включён |
| Документирование API | Swagger / OpenAPI | `Microsoft.AspNetCore.OpenApi` + `Swashbuckle.AspNetCore` |
| ORM | EF Core 10 + Npgsql | схема БД ведётся миграциями |
| СУБД | PostgreSQL 18 | локально и в `docker-compose.yml` |
| Тесты | NUnit + Moq, EF Core SQLite | CI не поднимает PostgreSQL |
| Инструменты | Visual Studio 2026, DBeaver, Git Extensions | см. отчёт об установке ПО |
| CI | GitHub Actions, `ubuntu-latest` | `.github/workflows/dotnet.yml` |

Решение содержит один проект приложения `Carsharing` и отдельный проект тестов.
Слои (`Api`, `Domain`, `Data`) разделяются папками внутри одного проекта, отдельные
сборки под них не выделяются.

## 1. Стиль кода (C# Conventions + StyleCop)

Во всех проектах решения подключён анализатор `StyleCop.Analyzers`. Предупреждения
анализатора считаются ошибками стиля и исправляются до открытия PR.

### Именование

| Элемент | Стиль | Пример |
|---|---|---|
| Класс, структура, record | PascalCase | `RentalService` |
| Интерфейс | `I` + PascalCase | `ICarRepository` |
| Метод | PascalCase, глагол | `CalculateTripCost()` |
| Асинхронный метод | суффикс `Async` | `GetFreeCarsAsync()` |
| Свойство, событие | PascalCase | `LicensePlate` |
| Константа | PascalCase | `MaxBookingMinutes` |
| Приватное поле | camelCase, без `_` | `bookingTimeout` |
| Параметр, локальная переменная | camelCase | `carId` |
| Enum | PascalCase, единственное число | `CarStatus.Booked` |
| Параметр типа | префикс `T` | `TEntity` |

### Форматирование

- Отступ: 4 пробела, табуляция не используется.
- Фигурные скобки обязательны даже для одной строки, открывающая скобка на новой строке.
- Один тип на файл, имя файла совпадает с именем типа.
- `using` размещаются вне namespace: сначала `System.*`, затем остальные по алфавиту.
- Длина строки не более 120 символов.
- Включена проверка nullable-типов (`<Nullable>enable</Nullable>`).
- Магические числа выносятся в константы или конфигурацию.

## 2. Ключевое слово `this`

- Обращение к полям, свойствам и методам экземпляра всегда через `this.` (правило StyleCop SA1101).
- В конструкторах `this.` обязателен, если имя поля совпадает с именем параметра.
- В статических членах `this` не используется.

```csharp
public sealed class Booking
{
    private readonly int carId;

    public Booking(int carId)
    {
        this.carId = carId;
    }
}
```

## 3. XML-документация

- Документируются все `public` и `protected` типы и члены.
- Обязательные теги: `<summary>`, `<param>`, `<returns>`, `<exception>` (если метод выбрасывает исключение).
- Дополнительно: `<remarks>`, `<example>`, `<see cref="..."/>`, `<inheritdoc/>` для реализаций интерфейсов.
- Используются только стандартные XML-теги, совместимые с Doxygen.
- Язык комментариев: русский. Комментарий объясняет, что делает член и зачем, а не пересказывает код.
- В `.csproj` включена генерация документации: `<GenerateDocumentationFile>true</GenerateDocumentationFile>`.

```csharp
/// <summary>
/// Рассчитывает стоимость поездки по выбранному тарифу с учетом скидки клиента.
/// </summary>
/// <param name="tripId">Идентификатор поездки.</param>
/// <returns>Итоговая стоимость в рублях.</returns>
/// <exception cref="ArgumentException">Поездка не найдена.</exception>
public decimal CalculateTripCost(int tripId)
```

## 4. Сообщения коммитов (Conventional Commits)

Формат: `<тип>(<область>): <краткое описание>`

Типы: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore`.

- Описание в повелительном наклонении, до 72 символов, без точки в конце.
- Один коммит содержит одно логическое изменение.
- Номер issue указывается в теле коммита: `Refs #12`.

Примеры:

```
feat(booking): add 15-minute booking timer
fix(tariff): correct discount calculation for regular clients
docs(readme): add project description
ci: add GitHub Actions workflow
```

## 5. Работа с ветками и Pull Request

- `master` является основной веткой. Прямые коммиты в неё запрещены (единственное исключение:
  первый коммит со структурой проекта).
- Любая задача начинается с issue.
- Ветка создаётся от `master` и называется `feature/<номер задачи>` — номер совпадает с первым
  числом в заголовке issue (порядок работ).
- Один issue = одна ветка = один PR.
- PR открывается в `master`, reviewer: MarinaPaley.
- В описании PR указывается связь с issue: `Closes #X` (или `Refs #X`, если issue не должен
  закрываться — например, issue с правилами работы).
- Слияние выполняется только после approve преподавателя. После слияния ветка удаляется.
- Перед открытием PR проект собирается, тесты проходят, конвейер GitHub Actions зелёный.

### Конвейер

Сборка и тесты автоматизированы в `.github/workflows/dotnet.yml`: `ubuntu-latest`,
.NET `10.0.x`, шаги `restore` → `build --configuration Release` → `test --no-build`.
Красный прогон означает, что PR не готов к ревью.

## 6. База данных (PostgreSQL 18)

- Имена таблиц и столбцов в `snake_case`, таблицы во множественном числе (`cars`, `trips`).
- Первичный ключ называется `id`, внешний: `<сущность>_id` (например, `car_id`).
- Изменения схемы выполняются миграциями EF Core (`dotnet ef migrations add <Name>`),
  файлы миграций коммитятся в репозиторий. Ручные SQL-скрипты допустимы только для разовых
  операций с данными.
- Денежные значения хранятся как `decimal(10,2)`, не `double`.
- Пароли и строки подключения не хранятся в репозитории (см. раздел 9).

## 7. Тесты

- Фреймворк: NUnit.
- Имя теста: `Метод_Сценарий_ОжидаемыйРезультат`, например
  `CalculateTripCost_RegularClient_AppliesDiscount`.
- Бизнес-логика (тарификация, бронирование, скидки) покрывается тестами.
- Тесты работают на EF Core SQLite и не требуют запущенного PostgreSQL.
- Время в тестах подменяется через `TimeProvider`, а не через `Thread.Sleep`.

## 8. Документация

- Документация в репозитории (README, conventions и т.п.) ведётся только в формате Markdown.
- Файлы для пояснительной записки КР ведутся в `.docx` в папке `kr-docs/`, скриншоты лежат рядом.
- Правила обработки бинарных файлов описаны в `.gitattributes`.
- Описание API поддерживается в актуальном состоянии: XML-комментарии в коде и Swagger UI.
- README отвечает на вопросы «что это», «как запустить», «что не входит в MVP».

## 9. Прочие договорённости

- Секреты (пароли, строки подключения, ключи) не коммитятся: используются
  `appsettings.Development.json` (добавлен в `.gitignore`) или переменные окружения.
- Названия проектов и решения осмысленные, на английском языке.
- Неиспользуемый код и закомментированные блоки в PR не попадают.

## Чек-лист перед открытием PR

- [ ] Ветка создана от `master` и названа `feature/<номер задачи>`.
- [ ] `dotnet build` проходит без предупреждений StyleCop.
- [ ] `dotnet test` зелёный.
- [ ] Все `public`-члены имеют XML-документацию.
- [ ] Коммиты оформлены по Conventional Commits, в теле указан `Refs #X`.
- [ ] В описании PR есть `Closes #X` или `Refs #X`, reviewer — MarinaPaley.
- [ ] В PR нет временных файлов, секретов и закомментированного кода.
